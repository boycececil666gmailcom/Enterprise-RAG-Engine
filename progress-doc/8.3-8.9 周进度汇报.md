### 8.3-8.9 Weekly Progress Report (English Version)

#### 1. One-Sentence Accomplishment Definition

Targeting a **3-person R&D team that needs to simultaneously consult internal technical documentation and large private source code**, and addressing the core pain points of **scattered materials, fragmented document-code relation, and untraceable evidence** during complex R&D problem analysis, we built an **augmented RAG retrieval pipeline incorporating multi-path retrieval, knowledge graph, and advanced contextual slicing (Contextual & Parent-Doc Retrieval)**, planning to reduce the **median duration for resolving a single issue (from initiating information lookup to securing the first set of citeable evidence)** from **45 minutes (currently being measured as baseline)** to **under 22.5 minutes (at least a 50% reduction, target value)**.

---

#### 2. Business Scenario & Process Boundaries

* **Direct Users**: A 3-person team of development/testing/architecture engineers involved in consulting internal tech docs, analyzing private source code, and conducting historical troubleshooting.
* **Process Owner**: Technical Leader / Knowledge Asset Lead of the R&D team.
* **Business Scenario**: When engineers handle complex R&D issues (e.g., cross-module bug troubleshooting, API behavior verification, architectural refactoring), they need to understand the background from design docs, API specifications, and Release Notes while navigating source code repositories to verify specific implementations.
* **Process Boundaries**:
  * **Start Point**: Receiving a complex R&D issue and initiating retrieval/location of relevant docs and code.
  * **End Point**: Finding a "citeable evidence chain" matching the root cause (including relevant doc clauses and specific code implementation lines) and confirming accurate positioning.
* **Core Bottlenecks**: Tool isolation between documentation and source code; low retrieval hit rates due to massive Chunks lacking context; semantic distortion caused by tearing 2D Markdown tables under traditional vector slicing.
* **Frequency & Impact**: Covers the core R&D team (3 people), averaging ~1 deep troubleshooting session per person per week (~3 times/week for the team). Unresolved, deep troubleshooting disrupts normal development momentum, and cross-module or onboarding troubleshooting remains extremely time-consuming.

#### 4. Weekly Progress Results & Evidence

This week focused on completing the architecture decoupling and core capability delivery of the **RAG Data Preprocessing Pipeline**, realizing an end-to-end data construction chain:

##### 4.1 Architecture Decoupling & Refactoring
* Decoupled model and code indexing implementations (previously concentrated in a few files) into Protocols, Registries, Factories, and Adapters.
* Refactored retrieval modes by deprecating the old mutually exclusive `hybrid/graph` mode, converting to a non-empty multi-path combination of `knowledge_graph / keyword / semantic`, and synchronizing Web, HTTP, MCP, and CLI interfaces.

##### 4.2 Core Preprocessing Pipeline Construction
* **Denoising & Filtering**: Automatically excluded non-technical QA legal files like `licenses/` (694KB), redundant legacy versions such as `release-notes/kanzi-3.0/` (88 files), and short text Page Stubs; unified Sphinx absolute URL syntax to reduce Token consumption.
* **Semantic Slicing & Structuring**: Performed semantic-level Chunk partitioning based on the `H1 > H2 > H3` hierarchy to prevent word-level fragmentation.
* **Markdown Table Flattening**: Automatically converted 2D Markdown tables into `Key: Value` natural language line lists, resolving vector retrieval issues with tabular structures.
* **Contextual Retrieval**: For long document slices, automatically synthesized `[Document Context: Title > Section]` headers onto Chunks to reduce vector retrieval distortion for isolated Chunks.
* **Parent-Document Retrieval**: Implemented a dual-layer context design featuring "small Chunks (200-250 words) for high-precision vector hits + automatic passthrough of Parent Content (1,500 words) to LLM".
* **Code/Text Hybrid Support**: Automatically identified C++, Lua, Java, and other code blocks vs. text descriptions, attaching metadata `chunk_type: "code"` and `code_lang`.
* **Global Deduplication & VDB-Ready Packaging**: Introduced SHA-256 hash deduplication to automatically generate a rich-metadata delivery-ready dataset `kanzi_rag_chunks.json.gz` (compressed 5.29MB / uncompressed 106.54MB).

##### 4.3 Delivery Evidence
* **Data Delivery**: Successfully exported standard dataset `kanzi_rag_chunks.json.gz`, containing highly structured metadata such as `source_url`, `local_path`, `page_title`, `section_path`, `chunk_type`, `code_lang`, and `hash`.
* **Code Merging**: Pipeline module decoupling and interface synchronization code have all been merged into the main branch.

#### 4. 本周项目推进结果及相关证据

本周重点完成了 **RAG 信息预处理管道（Data Preprocessing Pipeline）** 的底层架构解耦与核心能力落地，跑通了端到端的数据构建链路：

##### 4.1 架构解耦与重构
* 将原集中在少数文件中的模型与代码索引实现拆分为 Protocol、注册表、工厂和 Adapter。
* 重构检索模式，废弃旧有 `hybrid/graph` 互斥模式，调整为 `knowledge_graph / keyword / semantic` 的非空多路组合，并同步 Web、HTTP、MCP 与 CLI 接口。

##### 4.2 核心预处理 Pipeline 建设
* **降噪与过滤**：自动排除 `licenses/`（694KB）等非技术 QA 法规文件、`release-notes/kanzi-3.0/`（88个文件）旧版冗余，以及小文本 Page Stub；统一 Sphinx 绝对 URL 语法，降低 Token 消耗。
* **语义切片与结构化**：基于 `H1 > H2 > H3` 层次进行语义级 Chunk 划分，防止单字断裂。
* **Markdown 表格平坦化 (Table Flattening)**：将 2 维 Markdown 表格自动平坦化转换为 `Key: Value` 自然语言行列表，解决向量检索对表结构的识别难题。
* **Contextual Retrieval (文脉付与)**：针对长文档切片，自动在 Chunk 头部合成 `[Document Context: Title > Section]`，降低孤立 Chunk 的向量检索失真率。
* **Parent-Document Retrieval (双层检索)**：实现“小 Chunk (200-250字) 高精度向量命中 + 自动透传 Parent Content (1,500字) 给 LLM”的二重上下文设计。
* **代码/文本混合支持**：自动识别 C++、Lua、Java 等代码块与文本说明，自动打上 `chunk_type: "code"` 与 `code_lang` 元数据。
* **全局去重与 VDB Ready 打包**：引入 SHA-256 哈希去重，自动生成含 Rich Metadata 的一键投递数据集 `kanzi_rag_chunks.json.gz`（压缩版 5.29MB / 解压后 106.54MB）。

##### 4.3 交付证据
